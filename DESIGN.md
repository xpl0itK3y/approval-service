# DESIGN.md

## Модель данных

**approval_requests** — основная сущность.

| Поле | Тип | Комментарий |
|---|---|---|
| id | uuid (string) | PK |
| workspace_id | string | внешний id workspace, используется для изоляции данных |
| source_type | enum(publication, scenario, edit, external) | |
| source_id | string | внешний id материала, не валидируется сервисом |
| title, description | string/text | |
| reviewer_user_ids | json (list[string]) | внешние id пользователей, не email |
| status | enum(pending, approved, rejected, cancelled) | pending — начальное; остальные — финальные |
| created_by_user_id | string | из auth-контекста |
| created_at, updated_at | timestamp | |
| decided_by_user_id, decided_at | | заполняются при approve/reject/cancel |
| decision_comment | text | только для approve |
| decision_reason | text | для reject/cancel |

**audit_log_entries** — неизменяемый журнал: кто (`actor_user_id`), что
(`action`: create/approve/reject/cancel), когда (`created_at`), из какого
статуса в какой (`from_status`/`to_status`), с какими деталями (`details`,
JSON с comment/reason). Одна запись на каждое успешное действие. Доступен
через `GET .../approval-requests/{id}/audit-log` — это не требовалось явно
в ТЗ, но раз требование "оставлять след, по которому понятно, кто и что
изменил" сформулировано как наблюдаемое свойство, я сделал его проверяемым
через API, а не только как факт наличия таблицы.

**outbox_events** — таблица для интеграции по событиям (см. ниже).

**idempotency_keys** — записи `(workspace_id, endpoint, idempotency_key) →
(request_hash, response_status_code, response_body)`, уникальный индекс по
первым трём полям.

Все таблицы, кроме `idempotency_keys`, ссылаются на `workspace_id`; ни один
запрос в коде не обращается к `approval_requests` без фильтра по
`workspace_id`, взятому из авторизованного контекста, а не только из URL.

## Границы сервиса

Сервис не знает ничего о публикациях, сценариях, готовых материалах,
пользователях или workspace, кроме их id. Он не проверяет, существует ли
`sourceId`/`reviewerUserIds`/`workspace_id` в других системах — это
осознанно оставлено вызывающей стороне (per ТЗ: "реализовывать соседние
сервисы не нужно"). Ответственность approval-service — только за жизненный
цикл самой заявки на согласование: создание → pending → ровно одно финальное
решение.

Все ответы возвращают только то, что было передано клиентом или сгенерировано
сервисом (id, статусы, timestamps). Никаких обращений к внешним сервисам,
секретов, email, storage keys, signed URLs или provider payloads сервис не
принимает и не хранит — в схемах Pydantic для create/decision используется
`extra="forbid"`, так что даже случайно переданные лишние поля (например,
email) будут отклонены с 422, а не тихо сохранены.

## Изоляция workspace

Two-layer защита:

1. Path (`{workspace_id}`) и auth-контекст (`X-Auth-Workspace-Id`) должны
   совпадать — иначе 403, ещё до похода в БД.
2. Каждый SELECT/UPDATE в `app/services/approval_service.py` fильтрует по
   `workspace_id`. Если id заявки существует, но принадлежит другому
   workspace, ответ — 404 (не 403), чтобы не подтверждать сам факт
   существования чужой заявки.

## Обработка повторов (идемпотентность)

Клиент может передать заголовок `Idempotency-Key` в `POST create/approve/
reject/cancel`. Ключ скопирован в связке `(workspace_id, endpoint,
idempotency_key)`:

- Для create endpoint — `endpoint = "create_approval_request"`.
- Для решений — `endpoint = "{action}:{request_id}"` (т.е. одинаковый ключ,
  использованный для approve на разных заявках, не конфликтует).

Поведение:

- Ключ не передан → обычная обработка, повторный вызов создаст новую
  заявку/попытается применить решение заново (и упрётся в проверку финального
  статуса, если применимо). Это осознанный выбор: без ключа сервис не может
  отличить "повтор" от "нового логического запроса".
- Ключ передан впервые → запрос выполняется, а хэш тела запроса + код ответа
  + тело ответа сохраняются в той же транзакции, что и основное изменение.
- Ключ передан повторно с тем же телом → возвращается сохранённый ответ,
  никакого нового изменения не происходит (нет дублей).
- Ключ передан повторно с другим телом → 409 `idempotency_key_conflict`
  (это почти всегда баг на стороне клиента — переиспользование ключа для
  другого запроса).
- Гонка (два одинаковых запроса одновременно) — уникальный индекс на
  `(workspace_id, endpoint, idempotency_key)` ловит дубликат на уровне БД,
  проигравшая транзакция получает `IdempotencyKeyConflict` → 409.

Дополнительно, независимо от Idempotency-Key: после финального решения
(`approved`/`rejected`/`cancelled`) любая последующая попытка approve/
reject/cancel без совпадающего ключа получает 409 `conflict` — это то, что
гарантирует инвариант "после финального решения заявка не должна переходить
в другое финальное состояние" даже если клиент не использовал ключи вовсе.

## События / интеграции

Транзакционный outbox: каждое успешное действие (`create`, `approve`,
`reject`, `cancel`) в той же транзакции, что и изменение
`approval_requests`, вставляет строку в `outbox_events`
(`event_type` вида `approval_request.created|approved|rejected|cancelled`,
JSON `payload` с id заявки, workspace, source, статусом, actor и временем).
Это гарантирует, что событие никогда не потеряется и не разойдётся с
фактическим состоянием (нет отдельного шага "запись в БД, потом отправка в
брокер", который мог бы упасть между ними).

Сам сервис не публикует события во внешний брокер — задача явно исключает
"соседние сервисы". `scripts/relay_outbox.py` — минимальная демонстрация
relay-процесса: poll необработанных строк, "публикация" (здесь — печать в
stdout), пометка `published_at`. В реальной интеграции этот скрипт
заменяется на consumer, публикующий в Kafka/RabbitMQ/SNS, либо на
CDC-коннектор (Debezium) поверх той же таблицы.

Payload события собирается только из полей, уже прошедших через публичный
API (id-шники, title/description/status/actor), поэтому в событиях не может
оказаться секретов, токенов, email, storage keys, signed URLs или provider
payloads — их у сервиса просто нет.

## Известные компромиссы

- **Схема тестов vs миграций**: тесты создают схему через
  `Base.metadata.create_all()` на in-memory SQLite, а не гоняют реальные
  Alembic-миграции. Модели — единственный источник истины, миграция
  сгенерирована автогенерацией из тех же моделей, так что расхождение
  маловероятно, но это не 100% гарантия эквивалентности на проде (Postgres).
  Компромисс в пользу скорости тестов; для полной уверенности можно добавить
  отдельный (более медленный) интеграционный прогон миграций против Postgres
  в CI.
- **Outbox без relay в проде**: relay-скрипт — просто демонстрация паттерна,
  не production-worker (нет ретраев/backoff, at-least-once не гарантирован
  за пределами одного прогона). Для прода нужен отдельный процесс с чёткой
  политикой доставки.
- **Idempotency-Key не обязателен**: сервис не требует ключ на mutating
  запросах (в ТЗ формат не специфицирован). Без ключа клиент отвечает за
  собственные повторы сам; сервис лишь гарантирует, что *финальное решение*
  не может быть переопределено, независимо от наличия ключа.
- **enum-статусы захардкожены**: если в будущем понадобится, например,
  статус "on_hold" или many-step workflow, потребуется миграция и
  расширение state machine в `approval_service._apply_decision` — сейчас
  сознательно оставлена простая трёхветочная модель, соответствующая ТЗ.
- **Список ревьюеров не используется для авторизации**: `reviewerUserIds`
  хранится как метаданные (кто должен смотреть), но decide/cancel endpoints
  не проверяют, что `actor_user_id` входит в этот список — авторизация
  целиком построена на action-based auth-заглушке (`approval:decide`), как
  и требует ТЗ. Если продукту нужно "только назначенный ревьюер может
  принять решение" — это отдельное бизнес-правило поверх текущей модели.
